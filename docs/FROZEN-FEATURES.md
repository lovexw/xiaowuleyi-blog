# 功能冻结清单

> **冻结 = 代码留着、入口关掉、不再当欠账。** 与「删除」的区别只有一条：删了要从 git 历史里捞回来，
> 留着只在「碰巧改到这里」时才有成本。所以判断标准不是「这功能好不好」，而是「它现在还占不占注意力」。
>
> 别和 [MAINTENANCE.md](./MAINTENANCE.md) 的 §2 混淆：那里冻结的是**部署形态**（Workers / 官网），
> 这里冻结的是**站内功能**（会员 / 排行榜 / 广场同步…）。两者互不影响。
>
> 首次冻结：2026-11-10。依据是线上真实用量（主站 7 天访问日志 + 两站库实查），不是主观判断。
> 拍板记录与理由见 [ROADMAP.md](./ROADMAP.md) 第四节。

## 二 · 冻结之后的三条规矩

1. **不再往上投资**。冻结项不新增功能、不改架构、不接新需求。有人提「能不能加个…」，
   默认答复是「先解冻再谈」。
2. **只修越权和崩溃**。冻结项出 bug，只修「能被绕过造成越权」和「拖垮正常使用」两类；
   界面不顺、文案不美、体验瑕疵一律不动。
3. **审计口径收窄**。跑安全 / 复杂度审计时，冻结项只审「关掉之后有没有残留入口能绕过」，
   不再审「功能完整度」。这条是为了止住一种循环：每次审计都给它补一层防线，越补越像在用的功能。

## 三 · 关掉之后怎么确认真的关了

改完设置不用发版，但**设置读有进程内缓存，改库不会立刻生效**——要么走后台设置页保存（写路径会
主动失效缓存），要么改完重启容器。验证四条即可：

```bash
# 1. 前台两个页面应当 404
curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: <域名>' http://127.0.0.1/member
curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: <域名>' http://127.0.0.1/rank

# 2. 会员接口应当 404（logout 例外，要能清掉残留 Cookie）
curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: <域名>' http://127.0.0.1/api/member/me

# 3. 前台导航里不该再出现「会员」药丸 / 排行榜链接
curl -s -H 'Host: <域名>' http://127.0.0.1/ | grep -c 'href="/member"'

# 4. 评论区必须照常（圈层关掉后，所有评论对所有人可见）
curl -s -H 'Host: <域名>' http://127.0.0.1/post/<随便一篇有评论的> | grep -c 'cmt-gated'
```

第 4 条是最容易翻车的一条：圈层门槛（`commentGateTier`）与会员开关是**两个独立键**。
只关 `membersEnabled` 不动圈层，高档位会员的历史评论会因为「谁都不是会员了」而永久隐藏——
线上主站有 1.5 万条评论带 `member_id`。所以关会员必须同时把 `commentGateTier` 清空。

## 四 · 与「删除」的边界

冻结不等于永不动它。下面这些情况才值得真删：

- 某块代码**挡住了必须做的改动**（例如重构要改它的接口，而它已经没人用）
- 它带着**真实风险**且没人维护（例如对外接口有鉴权口子，冻结状态下仍需每次盯）
- 它让新部署者**误以为必须配置**（配置项比功能本身更容易造成困惑）

2026-11-10 盘点过一轮「真删」候选（MCP 服务器 478 行、英文版 254 行、demo 1,954 行、
partner 291 行），结论是**先不删**：删代码的收益是省心，而冻结已经拿到了省心，
删的动作只会把「万一要复活」的成本推到 git 历史里。等哪天其中某块真的挡路了再动。
