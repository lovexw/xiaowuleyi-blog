# 跨站会员继承（分站模式）

> 2026-11 落地。场景：`blog.btchao.com` 做付费会员，`blog.xiaowuleyi.com` 做个人生活博客 + 轻付费内容。
> 在 btchao 付过费的人，到主站自动是「永久会员」。**单向授予，不做双向联邦。**

## 为什么是分站，不是「一号通」

两站是**两个独立实例**——各自 `TENANTS_DIR`、各自 `tenants.json`、各自 `blog.db`，不是同一实例的两个租户。

「一个账号通行两站」需要建身份中心、迁移现有会员、调和档位语义，为一个几十人的会员盘子付这个代价不划算。分站只付「一条单向通道」的成本：两站会员表互不读写，关联只落在 `members.remote_issuer` / `members.remote_subject` 两列上。

## 通道长什么样

```
blog.btchao.com（来源站）                blog.xiaowuleyi.com（权益站）
  付费会员，自有会员表         ──推送──▶      永久会员，自有会员表
  后台分配永久档时发一条                   按邮箱认领，授予永久档
      HMAC 签名，5 分钟窗口                    失败只降级到「待认领」
```

特点：

- **触发点在后台，不在支付回调**——项目没有在线支付，`paid` 只是档位来源标注。来源站的会员是站长手动开的，开完顺手推一条。
- **无状态签名**：接收端本地验签，不回呼来源站。少一个故障点，也不需要公网互相可达之外的任何协调。
- **幂等**：同一 `(issuer, subject)` 重复推送按更新处理，改邮箱/改档位再推一次不会产生两条记录。

## 数据模型

| 位置 | 字段 | 含义 |
|---|---|---|
| `members.remote_issuer` | 来源站标识（如 `btchao`） | 空串 = 本地原生会员，不走继承 |
| `members.remote_subject` | 来源站会员 id | 唯一索引 `idx_members_remote`，一个来源会员只能绑一个本地账号 |
| `members.tier_source` | `partner` | 档位来源标注（只做展示，不参与权限判定） |
| `partner_grants` | 一行一条推送记录 | `member_id`：`0` 待认领 / `-1` 认领冲突 / 正数 已授予的本地会员 |

`partner_grants` 既是队列也是审计流水，后台「会员 → 跨站继承」直接读它，也进每晚备份。

## 端点与签名

接收端：`POST /api/partner/grant`

```
X-Partner-Signature: HMAC-SHA256(secret, [issuer, subject, email, tier, note, exp].join("\n"))
```

请求体：

```json
{ "issuer": "btchao", "subject": "7", "email": "reader@qq.com",
  "tier": "lifetime", "note": "btchao 付费会员", "exp": 1793856570619 }
```

| 情况 | 响应 |
|---|---|
| 本站没配 `partnerPushSecret` | `404`（不暴露「功能存在但没开」） |
| 签名不对 | `401` |
| `exp` 超出 ±5 分钟 | `400` |
| 档位不存在**或不是永久档** | `400`，附档位 key |
| 命中已有会员 | `200 {"result":"granted"}` |
| 没有这个邮箱的会员 | `200 {"result":"pending"}` |
| 该来源会员已绑别的账号 | `200 {"result":"conflict"}` |

## 两站怎么配

**权益站（xiaowuleyi）**

1. 会员设置 → 会员档位 → 加一档，key 填 `lifetime`，名称「永久会员」，勾永久。
2. 会员设置 → 跨站继承：本站标识填 `xiaowuleyi`，共享密钥填一个长随机串，推送地址留空。

**来源站（btchao）**

1. 同样有一档 `lifetime`（推的是**本站档位 key**，两站必须同名）。
2. 会员设置 → 跨站继承：本站标识填 `btchao`，推送地址填 `https://blog.xiaowuleyi.com`，共享密钥填**同一个**值。

密钥两端必须一致；`SECRET_SETTINGS` 里已登记，接口返回的是掩码，原样提交等于不修改。

## 认领规则

- 来源站会员在权益站**注册**或**登录**时，只要邮箱对得上，就自动升到永久档。
- 只升不降：本来就在更高档的，只记绑定关系，不动档位。
- 注册时邮箱**必填**（两次输入一致才放行），所以新会员不会再出现「没邮箱认领不到」这一态；存量没邮箱的老会员需要后台手动分配，或以后补一个「一次性补填邮箱」入口
- 邮箱大小写不敏感（`LOWER(email)` 比较，带表达式索引）；注册写库时已统一转小写

## 已知风险与防线

**主站注册不验证邮箱**（邮件服务尚未落地），只保证「必填 + 两次输入一致 + 一邮箱一账号」。理论上，填别人的付费邮箱能白拿永久会员。两道闸：

1. `(issuer, subject)` 唯一——先到先得，真会员后到时拿不到，站长能看到「认领冲突」；
2. 后台逐条记录来源、邮箱、时间，一键撤销。

**只有永久档会推送、也只接受永久档。** 限时档（年费）不在通道里，否则接收端置空有效期等于把年费偷偷变成终身。

**「永久」是真的永久**：来源站会员后来到期、退款，权益站不跟着收回。要收只能站长手动撤销——这是刻意选的简化，不是遗漏。

## 日常怎么用

1. btchao 后台给某人开永久档 → 自动推送 → 权益站「跨站继承」出现一条记录。
2. 对方在权益站注册（填同一个邮箱）→ 立刻是永久会员。
3. 已经注册过但没填邮箱的：直接在权益站后台手动分配永久档，或让他补邮箱后重新登录。

推送失败（对方站点抖动）不会回滚本地授予，后台分配档位的提示里会带 `partner: failed:...`，重开一次档位即可重推。

## 未来

- 邮件服务落地后，在认领处补一道「邮箱验证」即可堵上冒领，接口形状不用改。
- 要接第三个站，复制一份来源站配置即可，`issuer` 区分来源；无需改代码。
